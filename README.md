# catscriptor

Android-приложение для хакатона Nuclear IT Hack. Превращает аудиозаписи разговоров в расшифровку со спикерами и таймкодами. Вся обработка выполняется на устройстве, без интернета.

**Статус:** подготовлен каркас проекта, реализованы отдельные этапы декодирования
аудио и экспорта. Сквозной пайплайн и распознавание пока не реализованы.

## Контракты пайплайна

В `app/src/main/java/org/cfm/catscriptor/` выделены границы `ui`, `viewmodel`,
`domain/pipeline` и `native/models`. Пока это контракты, а не рабочий инференс.
Новых Gradle-модулей нет. Для экспорта добавлены Gson, Android-корутины и Lifecycle.

- Этапы: `AudioDecoder` → `VoiceActivityDetector` → `TranscriptionBackend` →
  `DiarizationBackend` → `UtteranceMerger` → `TextCorrectionBackend` → `TranscriptExporter`.
- PCM-источник даёт 16 кГц mono порциями по абсолютному смещению в **сэмплах**.
  Все интервалы и слова используют **миллисекунды от начала исходной записи**.
  Источник принадлежит вызывающему коду; модельные backend реализуют `ModelResource`
  и закрываются после своего этапа, включая ошибки и отмену.
- ASR возвращает `TimedWord`: исходное слово и его индивидуальный интервал.
  Спикер назначается каждому слову по пересечению с интервалами диаризации, затем
  слова объединяются в реплики. Равномерное деление интервала вместо реального
  выравнивания слов не допускается. Поддержку такого выравнивания нужно проверить
  при выборе ASR в #5/#12; отсутствие поддержки должно давать ошибку, не выдуманные метки.
- `Utterance` сохраняет исходные слова и их интервалы. LLM возвращает только
  исправленный текст; применяем `copy(text = ...)`, сохраняя спикера и выравнивание.
  Новым/изменённым LLM-словам не приписываются фиктивные пословные таймкоды:
  внутренние `words` относятся к исходному ASR-тексту.
- `Transcript.transcript` отсортирован по началу реплик, перекрытия допустимы.
  Контракт JSON не меняется: экспортируются только `speaker_id`, `start_ms`,
  `end_ms`, `text` внутри `transcript`; внутренние `words` не экспортируются.
   `DefaultTranscriptExporter` реализует JSON/TEXT, схема проверяется JVM-тестами.
- Длительные методы — `suspend`. Конкретные реализации должны выполнять тяжёлую
  работу вне UI-потока, поддерживать отмену и передавать ошибки вызывающему коду.
   Фоновый запуск подготовки аудио реализован отдельно; оркестрация остальных
   этапов, fallback и настоящие модели ещё не реализованы.

Контрактные JVM-тесты используют подмены только в `src/test`; они проверяют модель,
передачу пословного выравнивания и заменяемость этапов, но не качество распознавания,
алгоритм объединения или освобождение ресурсов настоящих моделей.

```bash
./gradlew :app:testDebugUnitTest :app:lintDebug
./gradlew assembleDebug assembleRelease test
```

## Экспорт JSON и TEXT

`DefaultTranscriptExporter` принимает существующий `Transcript` и пишет UTF-8 в
переданный `OutputStream`: не закрывает его, не сортирует реплики и не экспортирует
`words`. Gson `JsonWriter` используется без рефлексии и промежуточного JSON-дерева;
временные метки записываются как целые `Long`. TEXT использует формат
`[00:00:01.250 - 00:00:04.380] speaker_1: Добрый день!`, с переводом строки после
каждой реплики; число часов не ограничено двумя разрядами.

Для будущего экрана результата:

1. В `Activity.onCreate`, до `STARTED`, создать `ContentResolverTranscriptWriter`
   с `applicationContext.contentResolver` и `DefaultTranscriptExporter()`.
2. Создать `TranscriptExportController(activity, writer, onResult)`. Обработчик
   получает `Result<Uri>`: успех либо ошибку открытия/записи/закрытия документа.
3. На главном потоке вызвать `controller.export(transcript, TranscriptFormat.JSON,
   "transcript.json")` либо TEXT с именем `transcript.txt`, передав **реальный**
   результат пайплайна. Возвращаемое `false` означает занятость контроллера.
4. После пересоздания Activity использовать тот же ключ контроллера. Запрос и
   запись сохраняются во ViewModel при смене конфигурации, но не при смерти процесса.

Контроллер открывает `CreateDocument` с `application/json` или `text/plain`.
Отмена выбора не вызывает ошибку или запись. SAF позволяет пользователю самому
выбрать документ; широкие разрешения на хранилище не нужны. Открытие, запись и
закрытие потока выполняются на `Dispatchers.IO`; корутины обеспечивают фоновую
запись и отмену. Экран экспорта пока не подключён: готовой расшифровки
и демонстрационных данных в production-коде нет.

Проверки:

```bash
./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleDebug
./gradlew :app:connectedDebugAndroidTest
```

`DefaultTranscriptExporterTest` проверяет схему, экранирование, UTF-8, порядок,
перекрытия, большие метки и владение потоком. `ContentResolverTranscriptWriterTest`
использует провайдер только тестового APK: проверяет настоящий ContentResolver,
фоновую запись, закрытие при успехе/ошибке/отмене, MIME и отмену выбора.
Внешнее окно DocumentsUI и поворот экрана требуют отдельной ручной проверки
после подключения к экрану с настоящим `Transcript`. При ошибке провайдер может
оставить частично записанный документ; блокирующая операция провайдера не всегда
прерывается сразу при отмене. Поток `null` и ошибка закрытия обработаны кодом,
но пока не воспроизведены инструментальным тестом.

## Импорт и декодирование аудио

Реализации находятся в `audio/`, математическое ядро и WAV-парсер — в
`audio/core/`. Контракты `AudioDecoder` и `PcmAudioSource` не изменены.
Основной экран позволяет выбрать настоящий локальный документ через SAF и
запустить подготовку аудио в foreground service. Распознавание ещё не подключено.

- Сжатые MP3, M4A (AAC) и OGG (Vorbis) обрабатываются через Android
  `MediaExtractor`/`MediaCodec`. Поддержка конкретного кодека зависит от устройства;
  неподдерживаемые форматы должны возвращать ошибку, а не фиктивный результат.
- RIFF/WAVE читается отдельным потоковым парсером: integer PCM 8/16/24/32-bit,
  float32, включая поддерживаемый WAVE_FORMAT_EXTENSIBLE с полным числом значащих
  бит. Другие WAV-кодировки, RF64 и RIFX не поддерживаются.
- Каналы усредняются в mono; сэмплы приводятся к float в диапазоне `[-1, 1]`.
  Ресемплинг в 16 кГц использует оконный sinc с НЧ-фильтром. Фаза задаётся общим
  целочисленным номером выходного отсчёта, не сбрасывается на границах блоков.
  Число отсчётов округляется к ближайшему целому от `inputFrames × 16000 / rate`
  (половина вверх). Это ограничивает ошибку длительности половиной выходного
  отсчёта, независимо от длины записи; codec delay/padding проверяется отдельно.
  Коэффициенты повторяющихся фаз вычисляются один раз: для 44,1 кГц это 160 фаз,
  для 48 кГц — одна. Таблица ограничена 4 МиБ; при превышении лимита используется
  исходный расчёт. Фильтр и результат не изменены: тест сравнивает PCM с исходным
  алгоритмом без допуска, включая границы блоков и частоту с fallback.
- Оригинал копируется блоками в закрытый cache, чтобы даже потоковый SAF-документ
  стал seekable. Результат хранится как временный little-endian float32 PCM:
  около 230 МБ на час, плюс место для копии оригинала во время декодирования.
  Полная запись в оперативную память не загружается.
- Полученный источник принадлежит вызывающему коду: закрывайте его через `use`
  после последнего аудиоэтапа, включая ошибки и отмену. `close()` удаляет
  принадлежащий источнику PCM-файл. Незавершённые файлы удаляются при сбое.

Приложение не запрашивает `INTERNET` и не использует сетевые API. SAF-провайдер
является отдельным приложением: даже `EXTRA_LOCAL_ONLY` не даёт абсолютной
гарантии, что сторонний провайдер сам не обращается к сети. Для автономной
проверки выбирайте документ из локального хранилища устройства.

Использование декодера отдельно от сервиса:

1. В `Activity.onCreate` до `STARTED` создать `AndroidAudioDecoder(applicationContext)`
   и `AudioImportController(activity, onResult)`. После пересоздания использовать
   тот же ключ регистрации.
2. На главном потоке вызвать `controller.launch()`. Успешный callback получает
   `AudioInput` с непрозрачным `content://` URI; отмена picker не вызывает callback.
3. Сразу передать вход в `decoder.decode(input)` из корутины. Метод сам переключает
   работу на IO. Временное SAF-разрешение не сохраняется для последующих запусков
   приложения. Контроллер не владеет ни корутиной, ни PCM.
4. Полученный источник читать через `read(startSample, maxSamples)` и закрывать
   через `use`. Частичное чтение допустимо: файловая реализация возвращает не более
   16384 отсчётов за вызов, пустой массив — при достижении конца.

Долгоживущая подготовка из основного экрана запускается в `AudioProcessingService`.
Будущий пайплайн должен потреблять PCM внутри принадлежащего сервису `use`.
Блокирующее чтение стороннего провайдера может задержать отмену до возврата `read()`.
Для остатков после смерти процесса предусмотрена уборка собственных каталогов
старше суток при следующем декодировании; файловый lock защищает активные источники.

Ограничения платформенного декодирования: метаданные encoder delay/padding
передаются кодеку без повторной обрезки на стороне приложения. Корректность
gapless-длительности MP3/AAC и обработки MP4 edit list нужно подтвердить на
целевых устройствах: универсальной гарантии для OEM-кодеков нет. Android может
декодировать пригодный префикс повреждённого сжатого файла или скрыть ошибку кадра;
успешный EOS сам по себе не доказывает целостность оригинала. Структурные ошибки
WAV проверяются собственным парсером, ошибки extractor/codec передаются вызывающему коду.

Синтетические MP3/M4A/OGG для instrumentation-тестов лежат исключительно в
`app/src/androidTest/assets/audio/`; команды генерации приведены там же.
Они не включаются в основной APK и не используются production-пайплайном.

Проверка реализации #3:

```bash
./gradlew assembleDebug assembleRelease test :app:lintDebug :app:compileDebugAndroidTestKotlin --offline
# После подключения Android-устройства:
./gradlew :app:connectedDebugAndroidTest
```

Локально прошли 30 JVM-тестов (ещё один opt-in бенчмарк пропущен обычным запуском),
включая сравнение оптимизации с исходным алгоритмом и 10 тестов аудиоядра: stereo/разрядности,
частоты 8/16/22,05/44,1/48/96 кГц, короткие сигналы, антиалиасинг, 10 минут
потокового PCM и 30 секунд ресемплинга с независимостью от границ блоков,
повреждения WAV и владение PCM-файлом. Debug/release собраны; release APK
не подписан. Lint: 0 ошибок, 14 предупреждений.

Отдельный JVM-бенчмарк ресемплера: Ryzen 7 7700, OpenJDK 25, 10 секунд mono,
3 прогрева, медиана 5 запусков с учётом создания таблицы. Для 44,1 кГц:
615,72 → 44,94 мс; для 48 кГц: 670,35 → 47,56 мс (примерно 14×).
Количество отсчётов и checksum совпали. Это результат только ресемплера на ПК,
не RTF полного декодирования и не подтверждение скорости Android-устройства.

На vivo V2538 (Android 16) прошли все 14 instrumentation-тестов: 8 декодирования,
5 экспорта и проверка контекста приложения. Проверены:
WAV/MP3/M4A/OGG, длительность сжатых файлов (эталон 1 с, допуск ±20 мс),
амплитуда и частота тона, SAF pipe, отмена, повреждённый WAV и очистка кэша.
Эта проверка подтверждает работу кодеков только на данном устройстве.
Длинный WAV (30 минут, stereo 44,1 кГц) был остановлен вручную из-за низкой
скорости до завершения теста. Повторный запуск после оптимизации прошёл проверку
30-минутного WAV, включая число отсчётов, тон, последовательное чтение и очистку.
Во время запуска vivo замораживал фоновый процесс; после открытия приложения
обработка продолжилась, поэтому время этого запуска не является чистым замером RTF.
Проверка длинного MP3 не стартовала из-за отсутствия тестового файла в закрытом
каталоге приложения. Длинный MP3 и ручной DocumentsUI пока не подтверждены.
Тестовый провайдер экспорта написан на Java: его отдельный процесс не имеет
доступа к Kotlin runtime основного APK; реальный IPC через ContentResolver сохранён.
Отдельно вручную проверить
DocumentsUI после подключения контроллера, длинные файлы, нехватку места,
разные OEM-кодеки и реальную скорость. JVM-тесты не подтверждают эти свойства
Android-платформы. Проверено содержимое основных APK: тестовых аудиофайлов в них нет.

## Фоновая подготовка аудио

1. Нажать «Выбрать аудиофайл» и выбрать локальную запись. На Android 13+
   приложение предлагает разрешить уведомления; отказ не блокирует обработку.
2. Подготовка выполняется в foreground service с постоянным уведомлением
   и кнопкой отмены. Экран получает состояние через `StateFlow`; индикатор
   неопределённый, поскольку контракт декодера не сообщает процент выполнения.
3. При успехе показывается длительность записи. Сейчас PCM закрывается и удаляется
   после подготовки: это проверка аудиоэтапа, а не сохранённая расшифровка.
   В дальнейшем следующие этапы должны выполняться до закрытия PCM в сервисе.

Сервис использует тип `mediaProcessing` на Android 15+, `dataSync` на Android 11–14.
Частичный wake lock удерживает CPU только на время задачи, с ограничением 6 часов;
на завершении, ошибке, отмене и уничтожении сервиса он освобождается.
Сервис не перезапускается автоматически после смерти процесса и не сохраняет
разрешение SAF для будущего запуска. Системный тайм-аут отменяет задачу и останавливает
сервис; Android 15+ ограничивает суммарное время такого foreground-типа в фоне.

«Настроить работу в фоне» открывает системные настройки оптимизации батареи,
а при недоступности — страницу приложения. На vivo может потребоваться вручную
разрешить неограниченную фоновую работу. Foreground service и wake lock не дают
абсолютной гарантии против ограничений OEM, принудительной остановки или разрядки.
Экран постоянно включённым не удерживается; исключение из оптимизации автоматически
не запрашивается. Дополнительных сетевых разрешений нет.

## Сборка

Нужен Android Studio с установленными SDK, NDK и CMake.

```bash
./gradlew assembleDebug   # debug APK: app/build/outputs/apk/debug/app-debug.apk
./gradlew test            # юнит-тесты
```

Приложение поддерживает только архитектуру `arm64-v8a`.
